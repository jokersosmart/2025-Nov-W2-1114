# Feature Specification: SEooC 開發計畫 (ISO-26262 ASIL B + ASPICE)

**Feature Branch**: `001-seooc-iso26262-asil-b`  
**Created**: 2025-11-14  
**Status**: Draft  
**Input**: User description: "我想要做一個稽核流程的文件計畫，目標是能通過 ISO-26262 ASIL B 等級以及兼容 ASPICE 的開發計畫，產品是 PCIE Gen5 的 Controller 相關晶片，希望你先規畫一個 SEooC 的計劃書給我"

## Project Overview

**專案類型**: 文件開發專案 (Documentation Development Project)  
**測試策略**: Verification-First (Checklist-Driven Development)  
**憲法依據**: `.specify/memory/constitution.md` v1.2.0 §專案類型定義與測試優先原則適用性

**說明**: 本專案產出為 ISO-26262 合規文件模板、流程定義文件與檢查清單（非應用程式開發）。依據專案憲法 v1.2.0，文件開發專案採用「驗證優先（Verification-First）」替代傳統「測試優先（TDD）」，實踐方式為**檢查表驅動開發（Checklist-Driven Development, CDD）**：

1. **撰寫合規檢查表** → 定義驗證標準（等同於 TDD 的「寫測試」）
2. **建立文件模板** → 實作內容結構（等同於 TDD 的「實作」）
3. **試點驗證** → 以實際案例測試模板（等同於 TDD 的「執行測試」）
4. **檢查表驗證** → 依檢查表審查試點輸出（等同於 TDD 的「測試通過」）
5. **模板修訂** → 根據驗證結果改進（等同於 TDD 的「重構」）

**驗收測試定義**: 每個文件模板至少有一個**三方審查流程**（作者 → 審查者 → 批准者）並定義明確驗收標準。整合測試調整為**跨文件一致性驗證**（追溯矩陣完整性、版本號一致性、術語表對齊）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立 SEooC 假設與邊界定義 (Priority: P1)

開發團隊需要定義 SEooC（Safety Element out of Context）元件的假設、預期功能與使用情境，以便在沒有完整車輛系統資訊的情況下進行 PCIE Gen5 Controller 晶片的安全開發。

**Why this priority**: 這是 SEooC 開發的基礎，必須先明確定義假設與邊界才能進行後續所有安全活動。

**Independent Test**: 可透過審查假設文件的完整性與合理性來驗證，確保涵蓋所有必要的安全假設、功能範圍與外部介面定義。

**Acceptance Scenarios**:

1. **Given** 開發團隊開始 SEooC 專案，**When** 撰寫假設文件，**Then** 文件應包含：功能假設、安全目標、ASIL B 等級聲明、外部介面定義（包含 PCIE Gen5 核心協議與安全機制：CRC/ECC/鏈路訓練）、預期使用情境與限制條件
2. **Given** 假設文件草稿完成，**When** 提交審查，**Then** 安全工程師與技術負責人應確認假設的合理性與完整性
3. **Given** 假設文件經過審查，**When** 發現缺失或不一致，**Then** 團隊應修訂文件並重新審查直到通過

---

### User Story 2 - 建立符合 ISO-26262 Part 4 的開發流程文件 (Priority: P1)

開發團隊需要建立符合 ISO-26262 Part 4（產品開發：系統層級）與 ASPICE 要求的流程文件，包含需求管理、設計驗證、配置管理與變更控制。

**Why this priority**: 流程文件確保所有開發活動有明確依據與標準操作程序，避免因人員變動或經驗差異導致品質不穩定，提升團隊協作效率。

**Independent Test**: 可透過文件審查與流程模擬驗證，確保流程涵蓋 ISO-26262 Part 4 所有必要活動，並與 ASPICE 流程模型對齊。

**Acceptance Scenarios**:

1. **Given** 開發團隊開始制定流程文件，**When** 撰寫需求管理流程，**Then** 流程應涵蓋：需求擷取、需求分析、需求驗證、需求追溯與變更管理
2. **Given** 流程文件完成初稿，**When** 進行內部審查，**Then** 品質工程師應確認流程符合 ISO-26262 Part 4 與 ASPICE SWE.1-SWE.6 要求
3. **Given** 流程文件通過審查，**When** 團隊開始執行開發活動，**Then** 所有活動應依據流程文件執行並產生相應工作產品

---

### User Story 3 - 建立安全分析與風險評估文件 (Priority: P2)

安全工程師需要進行危害分析與風險評估（HARA），識別 PCIE Gen5 Controller 在假設使用情境下的潛在危害，並確定 ASIL B 等級的安全目標。

**Why this priority**: 安全分析是確保產品安全性的基礎，必須在設計階段完成以指導後續設計決策。

**Independent Test**: 可透過審查 HARA 文件的完整性與追溯性驗證，確保所有識別的危害都有對應的安全目標與安全需求。

**Acceptance Scenarios**:

1. **Given** 安全工程師開始 HARA，**When** 分析 PCIE Gen5 Controller 的使用情境，**Then** 應識別所有潛在危害並依據 **ISO-26262-3 Table 1** 評估其嚴重度 (S0-S3)、曝露度 (E0-E4) 與可控性 (C0-C3)，並使用 ASIL 判定矩陣確定 ASIL 等級
2. **Given** HARA 完成，**When** 確定安全目標，**Then** 每個危害應有對應的安全目標並分配 ASIL 等級 (目標 ASIL B，需確保 S/E/C 組合符合 Table 1 要求)
3. **Given** 安全目標確定，**When** 衍生安全需求 (TSR - Technical Safety Requirements)，**Then** 安全需求應可追溯至安全目標並包含驗證準則（包含診斷覆蓋率 90% 目標）。**TSR 撰寫應確保 ASIL 等級正確繼承**：若安全目標為 ASIL B，衍生的 TSR 必須至少為 ASIL B 或更高等級，不可降級

### User Story 4 - 建立測試檢查計畫（確保晶片功能正確且安全）(Priority: P2)

測試工程師需要建立符合 ISO-26262 Part 4 的測試檢查計畫，定義如何測試、測試哪些項目、以及如何判斷測試通過，確保 SEooC 元件符合所有功能與安全需求。

**名詞解釋**：V&V（Verification and Validation）= 驗證與確認 = 測試檢查
- **Verification（驗證）**：檢查「我們做的東西對不對」（例如：程式碼是否符合設計規格）
- **Validation（確認）**：檢查「我們做的東西是不是客戶要的」（例如：晶片功能是否符合客戶需求）

**Why this priority**: 測試檢查計畫是確保產品品質與安全性的關鍵，必須在開發早期建立以指導測試活動。就像蓋房子前要先規劃好如何檢查每個環節，才能確保房子蓋好後安全又符合需求。

**Independent Test**: 可透過審查測試檢查計畫的完整性驗證，確保涵蓋所有需求並定義明確的通過標準。

**Acceptance Scenarios**:

1. **Given** 測試工程師開始制定測試檢查計畫，**When** 定義測試策略，**Then** 計畫應涵蓋：單元測試（測試小零件）、整合測試（測試零件組合）、系統測試（測試整體功能）與安全驗證測試（測試安全機制）
2. **Given** 測試檢查計畫完成，**When** 進行審查，**Then** 品質工程師應確認測試覆蓋率符合 ASIL B 要求（確保每一行程式碼、每個判斷分支都有被測試到）
3. **Given** 測試檢查計畫通過審查，**When** 執行測試，**Then** 所有測試結果應記錄並追溯至對應需求（每個測試都要能對應到「測試這個是為了驗證哪個需求」）

---

### User Story 5 - 建立配置管理與變更控制文件 (Priority: P3)

配置管理員需要建立配置管理計畫與變更控制流程，確保所有工作產品（文件、程式碼、測試案例）都受到版本控制與變更追蹤。

**Why this priority**: 配置管理確保專案可追溯性與可重現性，避免因版本混亂導致的整合問題或無法追查問題根源，可在初期流程建立後逐步完善。

**Independent Test**: 可透過審查配置管理工具設定與變更記錄驗證，確保所有工作產品都受到適當管理。

**Acceptance Scenarios**:

1. **Given** 配置管理員開始制定 CM 計畫，**When** 定義配置項目，**Then** 所有重要工作產品應列為配置項目並分配版本編號
2. **Given** CM 計畫完成，**When** 團隊提交變更，**Then** 所有變更應經過審查與核准才能合併至主分支
3. **Given** 變更控制流程執行，**When** 發生需求變更，**Then** 影響分析應評估變更對安全性與其他需求的影響

### Edge Cases

- 當假設的使用情境與實際應用不符時，如何處理？（答：SEooC 假設文件應明確定義邊界條件與**整合者責任檢查清單**（符合 ISO-26262-8 §14.4.6 整合假設要求），整合者發現假設不符時應立即回報，由功能安全工程師評估影響並決定調整方案：修訂假設文件、整合者補充措施或重新設計。**整合者檢查清單結構**（三大類，共 15-20 項）：
  - **類別 1 - 環境參數驗證**（5-7 項）：
    * 工作溫度範圍：實際 ≤ -40°C ~ 125°C（驗證方法：環境測試報告）
    * 電源電壓穩定性：波動 ≤ ±5%（驗證方法：電源監控數據）
    * EMI 抗干擾等級：≥ Class B（驗證方法：EMC 測試報告）
    * 濕度範圍：5% ~ 95% 非凝結（驗證方法：環境規格確認）
    * 振動與衝擊：符合 IEC 60068 標準（驗證方法：機械測試報告）
  - **類別 2 - 介面規格驗證**（6-8 項）：
    * PCIE Gen5 鏈路誤碼率：< 10⁻¹²（驗證方法：鏈路品質分析儀測量）
    * 頻寬性能：≥ 32GT/s（驗證方法：頻寬測試）
    * 鏈路訓練時間：< 100ms（驗證方法：訓練序列分析）
    * 電氣參數：TX/RX 電壓擺幅符合 PCIE 5.0 規範（驗證方法：電氣測試）
    * 時脈精度：±300ppm（驗證方法：時脈分析）
    * 連接器類型與針腳定義：符合假設（驗證方法：硬體設計審查）
  - **類別 3 - 安全條件驗證**（4-5 項）：
    * 外部看門狗機制：整合者系統提供獨立看門狗監控 PCIE Controller 回應（驗證方法：系統架構審查）
    * 故障通知機制：Controller 故障訊號能傳遞至整合者安全管理器（驗證方法：介面測試）
    * 安全狀態定義：Controller 進入安全狀態（Safe State）的條件與行為與整合者系統一致（驗證方法：安全概念審查）
    * ASIL 分解假設：若 Controller 假設外部系統分擔部分 ASIL 要求，需驗證外部系統 ASIL 等級（驗證方法：ASIL 分解文件審查）
  ）
- 當 ASIL B 要求與 ASPICE 流程發生衝突時，如何取捨？（答：以 ISO-26262 安全要求為優先，ASPICE 作為流程改善參考。當資源有限時，優先滿足稽核最低要求，理想流程後續迭代。由技術仲裁小組在 3 個工作日內決策並文件化理由）
- 當測試覆蓋率無法達到 ASIL B 要求時，如何處理？（答：進行根因分析識別未覆蓋原因（死碼、防禦性程式碼、測試工具限制、設計問題），採取改善措施（移除死碼、重構設計、更換測試工具、靜態分析補充）。若技術上無法達成 100%，透過安全論證說明未覆蓋部分不影響安全性並取得偏差批准）
- 當 Codebeamer 遷移延遲或失敗時，如何應對？（答：採階段性遷移策略，先試點後全面。若遷移失敗，保留 Word + Excel 手動流程作為後備方案，確保開發不中斷）
- 當手動追溯矩陣維護負擔過重導致審查率低於 95% 時，如何處理？（答：啟動「重點審查」機制，優先審查安全相關變更，簡化一般功能變更審查流程。若低於 90%，升級至品質工程師與技術負責人共同評估改善措施）
- 當稽核發現不符合項時，如何處理？（答：不符合項分為重大與輕微，指派負責人與完成期限（重大 7 天、輕微 14 天）。若同類不符合項重複 3 次以上，啟動流程改善。所有整改完成後由品質工程師驗證並取得稽核員確認）
- 當稽核時程延遲或提前時，如何調整？（答：延遲時利用額外時間補充文件細節與提高追溯矩陣完整性；提前時啟動快速通道模式，優先完成高風險文件、簡化低風險文件、延後非關鍵活動）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 文件計畫 MUST 定義 SEooC 元件的假設、預期功能、外部介面與使用情境
- **FR-002**: 文件計畫 MUST 包含符合 ISO-26262 Part 4 所有必要工作產品的模板與範例（初期以 Microsoft Word .docx 格式提供，未來遷移至 Codebeamer 需求管理工具）
- **FR-003**: 文件計畫 MUST 定義需求管理流程，涵蓋需求擷取、分析、驗證、追溯與變更管理
- **FR-004**: 文件計畫 MUST 定義安全分析流程，包含 HARA (依據 ISO-26262-3 §7.4.3 與 Table 1 執行 S/E/C 評估與 ASIL 判定)、安全目標確定與安全需求衍生。**TSR (技術安全需求) 衍生時必須確保 ASIL 等級正確繼承**（符合 ISO-26262-4 §6.4.1.2）：若安全目標為 ASIL B，衍生的 TSR 必須至少為 ASIL B，不可降級
- **FR-005**: 文件計畫 MUST 定義測試檢查計畫（V&V = Verification and Validation = 驗證與確認），採用**四階段測試策略**：單元測試 (Unit Testing)、整合測試 (Integration Testing)、系統測試 (System Testing)、安全驗證測試 (Safety Validation Testing)，並涵蓋測試案例設計方法與通過標準。**靜態驗證方法**應包含：程式碼審查 (Code Review, 符合 ISO-26262-4 §6.4.8)、靜態分析工具 (Static Analysis with **MISRA-C 分級合規**, 符合 §6.4.9)、設計審查 (Design Review)。**MISRA-C 合規等級**（針對 ASIL B 專案）：
  - **Mandatory 規則**（16 條）：100% 合規，無偏差允許
  - **Required 規則**（104 條）：≥98% 合規，偏差需提供安全論證（Safety Argument）並經功能安全工程師審批
  - **Advisory 規則**（23 條）：≥80% 合規，偏差需文件化理由但無需正式審批
  - **偏差管理**：所有偏差記錄於 MISRA-C Deviation Log，包含規則編號、偏差原因、影響評估、替代措施
  
  **測試工具驗證**應依 ISO-26262-8 §11 執行工具分類 (Tool Impact: TI1/TI2/TI3, Tool Confidence Level: TCL1/TCL2/TCL3) 與驗證流程，高影響工具 (TI1, 如覆蓋率分析工具) 需執行 TCL2-3 驗證
- **FR-006**: 文件計畫 MUST 定義配置管理與變更控制流程，確保所有工作產品受版本控制。**Git 分支策略**（簡化 Git Flow，符合 ISO-26262-8 §7.4.3 配置管理基線要求）：
  - **main 分支**: 審查通過的穩定版本，每次合併需完成分級審查矩陣要求的審查流程
  - **develop 分支**: 持續整合工作分支，日常開發的匯集點
  - **feature/* 分支**: 個別文件或功能開發分支（如 feature/seooc-assumption, feature/hara-report），開發完成後透過 Pull Request 合併至 develop
  - **合併規則**: 所有合併至 main 或 develop 需透過 Pull Request，並依文件類型執行分級審查（安全文件需三方審查，一般文件需同儕審查）
  - **基線管理**: 每個月末階段性審查通過後,從 main 分支打 tag 作為配置基線(如 v1.0-Month1-Review, v2.0-Month2-Review, v3.0-Month3-Final),tag 包含審查記錄與核准簽名
  - **工作產品命名規範**（符合 ISO-26262-8 §7.4.3 文件識別要求）：
    * **命名格式**: `<DocType>_<版本號>_<狀態>_<YYYYMMDD>.docx`
    * **DocType（文件類型代碼）**: SEooC-Assumption（SEooC假設文件）, Safety-Plan（安全計畫）, HARA-Report（危害分析報告）, TSR（技術安全需求）, VVPlan（驗證確認計畫）, Safety-Case（安全案例）, Traceability-Matrix（追溯矩陣）, CM-Plan（配置管理計畫）, Review-Record（審查記錄）
    * **版本號**: vX.Y（X=主版本：完成階段性審查時遞增，對應 Git tag；Y=次版本：內容實質修改但未審查時遞增）
    * **狀態標籤**: Draft（草稿，編輯中）, InReview（審查中）, Reviewed（審查完成有待修訂）, Approved（已核准無重大缺陷）
    * **日期**: YYYYMMDD 格式（最後修改日期）
    * **命名範例**: `SEooC-Assumption_v1.0_Draft_20251114.docx` → `SEooC-Assumption_v1.0_InReview_20251120.docx` → `SEooC-Assumption_v1.0_Approved_20251125.docx` → `SEooC-Assumption_v1.1_Draft_20251201.docx`（修訂後）
    * **Git Tag 對應**: Git tag `v1.0-Month1-Review` 對應所有核心文件均為 `v1.0_Approved` 狀態；`v2.0-Month2-Review` 對應 `v2.0_Approved`
    * **Codebeamer 遷移後**: Codebeamer 自動管理版本號與狀態，匯出 Word 時自動附加版本號與狀態標籤，保持檔名格式一致確保可追溯性
  - **變更控制**: 基線建立後的變更需提交變更申請(Change Request),經**四維度影響分析**與審查核准後才能合併:
    * **維度 1 - 安全影響**: 變更是否影響 ASIL 分配、安全機制設計、HARA 結論、TSR 定義(由功能安全工程師評估)
    * **維度 2 - 追溯影響**: 識別哪些相關需求/設計/測試文件需同步更新,確保追溯矩陣完整性(由品質工程師評估)
    * **維度 3 - 測試影響**: 確定需要重新執行哪些測試案例,評估回歸測試範圍(由測試工程師評估)
    * **維度 4 - 時程影響**: 評估變更導致的額外工作量與對里程碑的延遲影響(由專案經理/技術負責人評估)
  - **影響分析記錄**: 所有分析結果需記錄於 Change Request 表單,經品質工程師審查確認完整性後提交核准
- **FR-007**: 文件計畫 MUST 包含 ASIL B 等級所需的結構覆蓋率與功能覆蓋率要求（參考 ISO-26262-4:2018 Table 9）
- **FR-008**: 文件計畫 MUST 對齊 ASPICE SWE.1 至 SWE.6 流程領域，確保流程可評估性
- **FR-009**: 文件計畫 MUST 包含安全案例（Safety Case）架構，採用 **GSN (Goal Structuring Notation)** 標準方法（符合 ISO-26262-2 §6.4.10 推薦），展示如何系統性論證產品符合安全目標。GSN 架構應包含：
  - **Goals (目標)**: 頂層安全聲明與子目標分解
  - **Strategies (策略)**: 論證策略（如「透過分析」、「透過測試」）
  - **Evidence (證據)**: 支持性證據（HARA 報告、測試結果、審查記錄）
  - **Context (情境)**: 論證適用範圍與假設
  - **Assumptions (假設)**: 論證依賴的假設條件
- **FR-010**: 文件計畫 MUST 定義工作產品的審查與核准流程，確保所有關鍵文件經過適當審查。**採用分級審查矩陣**（符合 ISO-26262-2 §6.4.5 角色與責任要求）：
  - **安全文件審查** (HARA 報告、TSR、Safety Case、V&V 計畫、安全分析報告)：需三方審查：**功能安全工程師 (Functional Safety Engineer)** + **品質工程師 (Quality Engineer)** + **技術負責人 (Technical Lead)**。審查準則：符合 ISO-26262 相關章節要求、ASIL 正確性、追溯完整性。核准條件：三方均同意且無未解決的主要缺陷 (Major Defect)
  - **一般文件審查** (流程文件、配置管理計畫、一般需求規格)：需同儕審查 (Peer Review)：至少兩位相關領域工程師。審查準則：內容完整性、格式正確性、與專案一致性。核准條件：審查者同意且無未解決的主要缺陷
  - **審查記錄**：應包含審查者簽名、審查日期、發現的缺陷清單、缺陷解決狀態
- **FR-011**: 文件計畫 MUST 包含追溯矩陣模板，建立需求、設計、測試與驗證活動之間的雙向追溯（**初期由品質工程師手動維護，專案第 4-6 個月基於里程碑觸發條件啟動 Codebeamer 遷移後由工具自動產生**）。**追溯矩陣結構採用 ISO-26262-4 §7.4.3.8 標準結構**，包含以下追溯關係類型：
  - **向上追溯（Upward）**: 需求→安全目標、設計→需求、測試→需求
  - **向下追溯（Downward）**: 安全目標→需求、需求→設計、需求→測試
  - **橫向追溯（Horizontal）**: 需求間依賴關係、設計元件間介面關係
  - **驗證追溯（Verification）**: 測試結果→測試案例→需求、審查記錄→工作產品
- **FR-012**: 文件計畫 MUST 定義 PCIE Gen5 Controller 的功能安全概念，包含安全機制（CRC 檢查、ECC 錯誤修正、鏈路訓練錯誤偵測）與診斷覆蓋率（目標 90%，符合 ASIL B 高診斷覆蓋率推薦值）。**診斷覆蓋率計算方法**（符合 ISO-26262-5 §8）：
  - **計算公式**: 診斷覆蓋率 DC = (可偵測的單點故障數 + 可偵測的潛在故障數) / (總單點故障數 + 總潛在故障數) × 100%
  - **故障模式範圍**（與安全相關的硬體故障）：
    * **包含**: CRC 錯誤（資料傳輸損壞）、ECC 錯誤（記憶體位元翻轉）、鏈路訓練失敗（PHY 層通訊異常）、電源電壓異常、時鐘失效等可能導致安全目標違反的故障
    * **排除**: 效能降級（如頻寬下降但不影響功能正確性）、良性暫態故障（可自動恢復且不影響安全）、與安全無關的功能性故障
  - **目標值理由**: 90% 對應 ISO-26262-5 Table 5 對 ASIL B 的高診斷覆蓋率建議（60-90% 為中等，>90% 為高），選擇高診斷覆蓋率以提升安全餘裕
- **FR-013**: 文件計畫 MUST 定義開發風險管理與應變機制,確保產品開發過程中遇到工具問題、流程瓶頸、時程延遲或技術挑戰時,團隊有明確的應對策略與升級路徑,保障開發進度與產品品質(包含工具遷移風險、Word/Git 兼容性、手動追溯矩陣可行性、測試覆蓋率無法達標時的改善措施、ASIL B 與 ASPICE 衝突時的取捨原則、假設情境不符時的調整機制)
- **FR-014**: 文件計畫 MUST 定義外部審查(Functional Safety Assessment)準備流程與證據管理策略(符合 ISO-26262-2 §6.4.11),包含:**2階段準備活動**(3個月文件審查+6個月完整評估)、**3類核心檢查清單**(文件完整性10項+流程合規性8項+技術正確性7項,共25項)、**稽核問題分類應對機制**(重大/輕微/觀察項,含整改時程與驗證流程)、**證據打包結構**(10類文件夾含審查記錄與自我檢查結果)。詳細執行指引參考開發保障 §6

### Key Entities

- **SEooC 假設文件（SEooC Assumption Document）**: 定義元件的假設、邊界與預期使用情境，包含功能假設、安全假設、環境假設與整合假設
- **安全計畫（Safety Plan）**: 定義專案的安全管理活動、角色與責任、時程與里程碑
- **需求規格（Requirement Specification）**: 包含功能需求與安全需求，並建立與安全目標的追溯關係
- **設計規格（Design Specification）**: 定義系統架構、元件設計與安全機制實作
- **測試檢查計畫（Verification & Validation Plan, V&V Plan）**: 定義如何測試、測試哪些項目、以及如何判斷測試通過（例如：這個功能要測試 100 次都成功才算通過）
- **追溯矩陣（Traceability Matrix）**: 建立需求、設計、測試與驗證活動之間的雙向追溯（初期由品質工程師使用 Excel/Word 手動維護，Codebeamer 部署後自動產生）
- **安全案例（Safety Case）**: 論證產品如何符合安全目標，包含證據與論述結構

### 開發保障與風險緩解措施（Development Assurance & Risk Mitigation）

**核心理念**：本開發計畫的主要目標是**確保產品順利開發**，透過嚴謹的思考與規劃，建立完整的文件與規格，展示團隊有能力應對各種變因與挑戰。稽核合規是附帶的驗證，但不是唯一目的。我們希望透過全面的風險考量，讓任何接手專案的人都能理解我們的思考邏輯與應變措施。

#### 1. 工具與平台風險緩解

**風險場景**：
- **Codebeamer 遷移延遲或失敗**：若 Codebeamer 部署時程延遲、技術整合困難或供應商支援不足，可能影響追溯矩陣自動化與需求管理效率
- **Word 格式與 Git 版本控制兼容性問題**：Word .docx 為二進位格式，Git 無法有效進行差異比對與衝突解決，可能導致並行編輯衝突與版本管理困難
- **測試工具驗證需求（ISO-26262-8 §11）**：覆蓋率分析工具、靜態分析工具 (MISRA-C)、故障注入工具需依 Tool Impact (TI) 與 Tool Confidence Level (TCL) 分類並驗證，若工具未驗證可能導致外部評估不通過

**應對措施**：
- **階段性遷移策略**：Codebeamer 遷移採「先試點、後全面」原則，優先遷移追溯矩陣與高頻變更文件（如需求規格），成熟後再擴展至其他工作產品。若遷移失敗，保留 Word + Excel 手動流程作為後備方案
- **Word/Git 兼容性強化**：
  - 採用「單一作者鎖定」機制（每份文件同時只允許一人編輯，透過團隊溝通協調）
  - 重要版本里程碑同步匯出 PDF 作為不可變更的參考基準
  - 使用 Git LFS（Large File Storage）管理 Word 文件，減少儲存庫膨脹
  - 建立明確的文件命名與版本編號規範（如 `SEooC_Assumption_v1.2_20251114.docx`）
- **工具驗證策略（符合 ISO-26262-8 §11）**：
  - **工具分類標準**：
    * **TI1 (高影響)**：覆蓋率分析工具 (影響覆蓋率報告正確性) → 需 TCL2-3 驗證
    * **TI2 (中影響)**：靜態分析工具 (MISRA-C 檢查結果需人工審查) → 需 TCL1-2 驗證
    * **TI2 (中影響)**：故障注入工具 (測試結果需交叉驗證) → 需 TCL1-2 驗證
    * **TI3 (低影響)**：文件編輯工具 (Word/Git) → 無需正式驗證
  - **驗證方法選項**（依 TCL 等級）：
    * TCL1：工具供應商認證文件驗證
    * TCL2：工具使用案例驗證 (與已知正確結果比對)
    * TCL3：工具開發流程符合性驗證 (需供應商提供開發文件)
  - **應急計畫**：若工具驗證失敗或工具不可用，採用人工審查補充 (如人工計算覆蓋率、人工 MISRA-C 檢查)
- **工具失效應急計畫**：若 Codebeamer 或 Git 發生重大問題，團隊應能在 24 小時內切換至替代方案（如 SharePoint + Excel 或 Google Workspace），確保開發不中斷

#### 2. 流程執行風險緩解

**風險場景**：
- **手動追溯矩陣維護與 95% 變更審查率的可行性挑戰**：在 Codebeamer 部署前，品質工程師需手動維護追溯矩陣，若需求變更頻繁，可能無法及時更新或達成 95% 審查率目標
- **ASPICE Capability Level 2 與 1 個月文件計畫完成時限的時程壓力**：ASPICE Level 2 要求流程有明確定義、管理與執行證據，1 個月內建立完整流程文件可能面臨資源不足

**應對措施**：
- **追溯矩陣簡化策略**：
  - 初期僅追溯「高風險需求」（安全需求、ASIL B 關鍵需求）與「核心功能需求」，降低維護負擔
  - 採用「批次更新」模式（每週固定時段集中更新追溯矩陣，而非逐筆即時更新）
  - 若審查率低於 90%，啟動「重點審查」機制（優先審查安全相關變更，一般功能變更可簡化審查流程）
- **流程文件分階段交付**：
  - **1 個月目標**：完成核心流程框架（需求管理、安全分析、配置管理）與關鍵模板
  - **2-3 個月目標**：補充詳細操作指引、案例與審查檢查清單
  - 若 1 個月時限無法達成，優先確保「符合稽核最低要求的流程文件」完成，細節後續迭代補充

#### 3. 技術挑戰應變機制

**風險場景**：
- **測試覆蓋率無法達到 ASIL B 要求（100% 語句/分支覆蓋率）**：若程式碼架構複雜、測試工具限制或防禦性程式碼（defensive code）過多，可能無法達成覆蓋率目標
- **診斷覆蓋率 90% 目標無法實現**：若硬體設計限制導致某些故障模式無法診斷（如罕見的瞬態錯誤），可能無法達成診斷覆蓋率目標

**應對措施**：
- **覆蓋率無法達標時的改善流程**：
  1. **根因分析**：識別未覆蓋程式碼的原因（死碼、防禦性程式碼、測試工具限制、設計問題）
  2. **改善措施選項**：
     - 若為死碼（Dead Code）：移除或標註為「維護性程式碼」（需文件化理由）
     - 若為防禦性程式碼：評估是否可簡化設計或採用靜態分析工具證明其安全性
     - 若為測試工具限制：評估更換測試工具或採用人工審查補充
     - 若為設計問題：重構程式碼以提高可測試性（Testability）
  3. **偏差批准機制**：若技術上無法達成 100% 覆蓋率，透過安全論證（Safety Argument）說明未覆蓋部分不影響安全性，並取得安全工程師與技術負責人批准
- **診斷覆蓋率優化策略**：
  - 優先實作高效益診斷機制（CRC/ECC 錯誤偵測涵蓋大部分故障模式）
  - 若 90% 目標無法達成，降至 ISO-26262 Part 5 對 ASIL B 的最低要求（60-90% 範圍），並在安全案例中說明理由

#### 4. 標準衝突與取捨原則

**風險場景**：
- **ASIL B 與 ASPICE 要求衝突時的取捨困境**：某些情況下 ISO-26262 安全要求可能與 ASPICE 流程效率產生矛盾（如安全分析需要大量迭代，但 ASPICE 強調流程穩定性）

**應對措施**：
- **取捨原則金字塔**（優先順序由高至低）：
  1. **功能安全 > 流程效率**：當 ISO-26262 安全要求與 ASPICE 流程效率衝突時，以安全為優先
  2. **合規性 > 理想性**：當資源有限時，優先滿足稽核最低要求，理想流程後續改善
  3. **實用性 > 形式主義**：當流程文件過於繁瑣影響開發效率時，簡化流程但保留核心控制點
- **衝突解決機制**：當發生標準衝突時，由功能安全工程師、品質工程師與技術負責人組成「技術仲裁小組」，在 3 個工作日內做出決策並文件化理由

#### 5. 假設情境不符時的調整機制

**風險場景**：
- **SEooC 假設使用情境與實際應用不符**：整合者（Integrator）將 PCIE Gen5 Controller 整合至車輛系統時，發現實際使用情境超出假設範圍（如溫度範圍、電磁干擾強度、故障率要求）

**應對措施**：
- **假設驗證檢查清單**：在 SEooC 假設文件中明確列出**「整合者責任檢查清單」**（結構化三大類，共 15-20 項，詳見 Edge Cases 章節），包含：
  - **環境參數驗證**（5-7 項）：工作溫度、電源電壓、EMI 等級、濕度、振動與衝擊
  - **介面規格驗證**（6-8 項）：PCIE Gen5 誤碼率、頻寬、訓練時間、電氣參數、時脈精度、連接器定義
  - **安全條件驗證**（4-5 項）：外部看門狗、故障通知機制、安全狀態定義、ASIL 分解假設
- **假設不符時的處理流程**：
  1. **整合者回報**：整合者發現假設不符時，應立即回報給 SEooC 提供者（我們）
  2. **影響評估**：功能安全工程師評估假設變更對安全性的影響（是否影響 ASIL B 等級、是否需要重新進行 HARA）
  3. **調整方案**：
     - **方案 A**：修訂 SEooC 假設文件並重新驗證（若影響不大）
     - **方案 B**：整合者自行補充安全措施（若整合者環境特殊）
     - **方案 C**：重新設計 PCIE Gen5 Controller（若假設偏差過大）
  4. **追溯更新**:若採用方案 A,需更新追溯矩陣並重新審查受影響的安全需求與測試案例

#### 6. 外部審查準備流程與證據管理(符合 ISO-26262-2 §6.4.11)

**核心理念**:外部功能安全評估(Functional Safety Assessment)是 ISO-26262 強制要求,評估結果直接影響產品認證。明確的準備流程與證據管理策略可提升首次通過率,減少整改成本與時程延遲。本章節提供自包含的準備指引,團隊無需外部文件即可執行。

**6.1 兩階段準備活動**

階段 1 - 3個月文件審查準備(第2-3個月):準備時機為第2個月末HARA+TSR審查通過後。核心活動:(1)證據打包:彙整所有v2.0_Approved工作產品,(2)自我檢查:使用下方檢查清單執行內部預審,(3)缺口補強:整改重大不符合,(4)審查員溝通:提前2週提交文件包。

階段 2 - 6個月完整評估準備(第5-6個月):準備時機為第3個月末最終審查通過後。核心活動:(1)完整證據打包:所有v3.0_Approved工作產品+V&V執行記錄,(2)流程證據:ASPICE CL2評估+工具驗證記錄,(3)追溯性驗證:100%覆蓋率確認,(4)模擬審查:外部顧問執行Mock Assessment。

**6.2 外部審查檢查清單(25項)**

類別 1 - 文件完整性10項:(1)SEooC假設含4類假設,(2)HARA含S/E/C與ASIL判定,(3)安全目標含ASIL聲明,(4)TSR正確繼承ASIL,(5)V&V Plan涵4階段,(6)Safety Case採GSN,(7)追溯矩陣4類追溯100%,(8)CM Plan含Git策略+四維度變更控制,(9)審查記錄含簽名+缺陷清單,(10)所有文件遵循四段式命名。

類別 2 - 流程合規性8項:(1)安全文件經三方審查,(2)變更控制含四維度分析,(3)工具驗證涵蓋TI1工具TCL2-3,(4)MISRA-C達分級合規(M:100%/R:≥98%/A:≥80%),(5)Git符合簡化Git Flow,(6)ASPICE SWE.1-6有流程定義+執行證據,(7)分級審查矩陣記錄完整,(8)手動追溯矩陣維護3月+審查率≥95%。

類別 3 - 技術正確性7項:(1)診斷覆蓋率符合ISO-26262-5公式達90%,(2)結構覆蓋率100%(語句+分支),(3)功能覆蓋率100%,(4)安全機制含CRC/ECC/鏈路訓練,(5)整合者檢查清單3類15-20項,(6)HARA的S/E/C評估合理,(7)TSR可驗證性明確。

**6.3 稽核問題應對機制**

不符合項分類:重大(Major,7天整改,功能安全工程師主導)/輕微(Minor,14天整改,品質工程師主導)/觀察項(Observation,30天評估,技術負責人決策)。應對流程:24hr根因分析→48hr整改計畫→執行整改→品質工程師驗證→稽核員確認。預防措施:同類問題≥2次啟動流程改善。

**6.4 證據打包結構**(10類文件夾):1-SEooC-Assumption,2-Safety-Plan,3-HARA-Report,4-Safety-Goals-TSR,5-VV-Plan,6-Safety-Case,7-Traceability-Matrix,8-CM-Plan,9-Process-Evidence(ASPICE CL2+分級審查矩陣+變更控制Log+工具驗證),10-Summary-Checklist(自我檢查結果)。所有文件使用v3.0_Approved狀態對應Git tag v3.0-Month3-Final。

## Terminology

本章節定義 spec.md 中使用的關鍵術語與縮寫，提供 ISO-26262 標準條款參考。

### 安全相關術語

- **ASIL (Automotive Safety Integrity Level，汽車安全完整性等級)**: 風險分類方案，定義安全需求的嚴格程度，從 QM (Quality Management) 到 ASIL D 共五個等級。本專案目標為 ASIL B。參考：ISO-26262-1 §3.2

- **HARA (Hazard Analysis and Risk Assessment，危害分析與風險評估)**: 系統性識別危害情境、評估風險（嚴重度 S、曝露度 E、可控性 C）並判定 ASIL 等級的方法。參考：ISO-26262-3 §7

- **SEooC (Safety Element out of Context，脫離情境的安全元件)**: 在沒有完整車輛系統資訊的情況下開發的安全元件，需定義假設以支援後續整合。參考：ISO-26262-8 §14

- **Safety Goal (安全目標)**: 從 HARA 衍生的頂層安全需求，用於避免或緩解特定危害情境造成的不合理風險。參考：ISO-26262-3 §8

- **TSR (Technical Safety Requirement，技術安全需求)**: 從安全目標衍生的系統層級或元件層級安全需求，繼承 ASIL 等級。參考：ISO-26262-4 §6

- **Safety Case (安全案例)**: 系統性論證產品如何符合安全目標的結構化文件，包含論證邏輯、證據與假設。參考：ISO-26262-2 §6.4.10

- **GSN (Goal Structuring Notation，目標結構化標記法)**: 用於 Safety Case 的圖形化表示方法，包含 Goals（目標）、Strategies（策略）、Evidence（證據）、Context（情境）、Assumptions（假設）五種元素。業界標準方法。

- **Diagnostic Coverage (診斷覆蓋率)**: 安全機制能偵測到的故障數佔總故障數的比例。**計算公式**: DC = (可偵測單點故障 + 可偵測潛在故障) / (總單點故障 + 總潛在故障) × 100%。ASIL B 建議達 90% 以上（高診斷覆蓋率）。本專案包含 CRC/ECC/鏈路訓練失敗等安全相關硬體故障，排除安全無關的效能降級或良性故障。參考：ISO-26262-5 §8

### 開發流程術語

- **V&V (Verification and Validation，驗證與確認)**: 驗證（Verification）確認產品符合規格，確認（Validation）確認產品符合使用者需求。通稱「測試檢查」。參考：ISO-26262-8 §9-10

- **Traceability Matrix (追溯矩陣)**: 建立需求、設計、測試與驗證活動之間雙向追溯關係的表格，確保需求完整實作與測試。參考：ISO-26262-8 §6

- **Structural Coverage (結構覆蓋率)**: 程式碼結構被測試案例執行的比例，包含語句覆蓋率（Statement Coverage）、分支覆蓋率（Branch Coverage）。ASIL B 要求兩者均達 100%。參考：ISO-26262-6 §9, Table 12

- **Functional Coverage (功能覆蓋率)**: 需求被測試案例覆蓋的比例。本專案目標 100%（所有需求都有對應測試案例）。參考：ISO-26262-4 §7.4.9

- **Configuration Management (配置管理)**: 系統性控制工作產品版本、變更與發布的流程。本專案採用簡化 Git Flow 策略（main + develop + feature/* 分支），每月末審查後打 tag 建立配置基線。**工作產品命名採四段式結構**：`<DocType>_<版本號>_<狀態>_<日期>.docx`（如 `SEooC-Assumption_v1.2_Draft_20251114.docx`），支援 Word/Codebeamer 雙軌管理，與 Git tag 版本對應。參考：ISO-26262-8 §7

- **Work Product (工作產品)**: 開發過程產生的文件或程式碼產出物，如需求規格、設計文件、測試報告等。本專案所有工作產品遵循統一命名規範（文件類型代碼 + vX.Y 版本號 + 狀態標籤 + YYYYMMDD 日期），確保唯一識別與可追溯性。參考：ISO-26262-2 §5.4.7

- **Training & Competency (培訓與能力)**: 確保人員具備執行功能安全活動所需資格與能力的系統性方法。本專案採用三層分級培訓(基礎 16hr 全員 + 進階 24hr 角色專屬 + 專家層持續學習),結合筆試、實作演練與導師評估三重驗證機制,並建立季度能力檢核與新進人員快速通道(8hr 濃縮培訓)。參考:ISO-26262-2 §5.4.2

- **Metrics Collection (度量收集)**: 系統性收集Success Criteria達成數據的方法。本專案採分層機制:SC-001~003使用檢查清單逐項勾選,SC-004~005使用自動化工具報告(覆蓋率分析/靜態分析),SC-006~008使用評估記錄與滿意度調查,品質工程師每月彙總dashboard。參考:ISO-26262-2 §5.4.7

- **Configuration Item (配置項,CI)**: 受配置管理控制的工作產品。本專案採三層分類:Level 1關鍵文件(所有Approved工作產品),Level 2程式碼(source code+script),Level 3支援文件(會議記錄+決策email)。所有CI遵循四段式命名規範,變更需Change Request。參考:ISO-26262-8 §7.4.2

### 流程評估術語

- **ASPICE (Automotive SPICE，汽車軟體流程改進與能力評定)**: 汽車軟體開發流程評估標準，定義流程領域（如 SWE.1-SWE.6）與能力等級（Capability Level 0-5）。業界標準。

- **Capability Level (能力等級)**: ASPICE 流程成熟度評級，從 Level 0（未執行）到 Level 5（優化中）。本專案目標 Level 2（管理的流程）。參考：ASPICE PAM 3.1

- **SWE (Software Engineering，軟體工程)**: ASPICE 流程領域，包含 SWE.1（需求分析）、SWE.2（架構設計）、SWE.3（詳細設計與單元測試）、SWE.4（整合測試）、SWE.5（系統測試）、SWE.6（軟體驗收）。

### 工具相關術語

- **TI (Tool Impact，工具影響)**: 工具故障可能導致的安全風險等級，從 TI1（高影響，可能引入安全缺陷）到 TI3（低影響，不影響安全）。參考：ISO-26262-8 §11.4.3

- **TCL (Tool Confidence Level，工具信賴等級)**: 工具驗證所需的嚴格程度，從 TCL1（低，供應商認證）到 TCL3（高，開發流程驗證）。參考：ISO-26262-8 §11.4.4

### 其他縮寫

- **CRC (Cyclic Redundancy Check，循環冗餘檢查)**: 錯誤偵測演算法，用於 PCIE 資料傳輸完整性檢查
- **ECC (Error Correcting Code，錯誤修正碼)**: 自動偵測與修正記憶體錯誤的技術
- **PCIE (PCI Express)**: 高速串列電腦擴充匯流排標準，本專案針對 Gen5 (第五代) Controller
- **MISRA-C**: 汽車軟體 C 語言編碼標準，用於提升程式碼品質與安全性。包含 143 條規則：16 條 Mandatory（強制，100% 合規）、104 條 Required（必要，≥98% 合規）、23 條 Advisory（建議，≥80% 合規）。本專案採分級合規策略符合 ASIL B 要求
